# ADR-009 — Demo-mode infrastructure (replay API + in-memory app)

Status      :  Accepted
Date        :  2026-04-17
Deciders    :  Product, Data Science Team
Relates to  :  ADR-001 (Classical CV only), ADR-008 (algo-1.3.0 switch)

## Context

After Phase 5 landed the frontend we needed a low-friction way for
stakeholders to exercise the whole stack on their own machine — no
Docker, no Postgres install, no manual folder creation. The production
entrypoint (`tad.main:app` + `make up && make migrate && make serve`)
requires:

1. Docker Desktop running.
2. `.env` present with valid `DB_DSN`, `MINIO_*`, and folder paths.
3. Watched folders (`IMAGES_LEFT_DIR`, `IMAGES_RIGHT_DIR`) to exist.
4. Someone to drop paired L/R images on a cadence.

Each of those is a real barrier when the goal is *"double-click, see the
dashboard populate"*. During the initial walkthrough we hit all four on
a fresh Windows box.

We also observed that `watchdog.observers.Observer` on Windows (backed
by `ReadDirectoryChangesW`) silently drops `on_created` events when
the internal buffer overflows — consistently reproducible after a few
rapid write_bytes calls into the same folder. This does not affect
production (one-chassis-per-minute cadence), but it breaks demos where
the replay fires fast pairs.

## Decision

Add a second, demo-only entrypoint that coexists with the production
wiring:

1. **`scripts/run_demo.py`** — boots the FastAPI app via
   `tad.api.app.create_app(...)` with in-memory repositories (the
   same `InMemory*` fakes the integration tests use) and
   `InMemoryBlobStore`. Auto-creates `~/.tad/images/{left,right}`.

2. **`POST /v1/demo/replay/start`** (and `/stop`, `/status`) — a new
   router in `src/tad/api/routes_demo.py`, registered alongside the
   production routes but under the `/v1/demo/*` prefix so it's
   trivially grep-able and can be gated out in a production build
   via conditional `app.include_router()` if the security review
   ever asks.
   - Takes a `source_dir` (defaults to
     `tests/fixtures/test_images/yca_valid`) and an
     `interval_seconds`.
   - Pairs `*_L.jpg` / `*_R.jpg` files by sorted order.
   - Generates fresh 17-char VIN-compliant chassis numbers with a
     fixed `DMAX` prefix plus a base-32 index (no I / O / Q).
   - Feeds the consumer pipeline **directly**, bypassing the watchdog
     observer entirely — see "Why bypass the watcher" below.

3. **`frontend/src/pages/Dashboard.tsx`** — on mount, polls
   `/v1/demo/replay/status` and calls `/start` with `interval=20` if
   nothing is running. Renders a blue banner
   *"Demo replay: streaming — N / 321 chassis sent at 20s intervals"*
   so it's always visually obvious that you're in demo mode.

4. **Band widening in the demo overlay only** — `run_demo.py` applies
   a `model_copy` overlay to `algo-1.3.0` with wider PASS / REVIEW
   bands (ok=1.0 mm, somewhat_ok=1.5 mm, asymmetry=2.5 mm). This is
   NOT a production change; the committed `algo-1.3.0.yaml` is
   unchanged.

## Alternatives considered

- **Require Docker for all demos.** Rejected — getting Docker Desktop
  running on a fresh Windows box is a 15-minute yak-shave for a
  5-minute demo.
- **Seed the database with canned data.** Rejected — doesn't exercise
  the full pipeline (session, SSE, aggregator, status matrix). The
  point of the demo is that stakeholders see the *live* flow.
- **Rely on the folder watcher for the replay.** Tried first. Dropped
  because of the Windows ReadDirectoryChangesW overflow described
  above — pairs disappeared silently under rapid cadence.

## Consequences

### Positive

- One command (`make demo`) boots the backend with zero preconditions.
- The frontend auto-starts the replay — opening the Dashboard fills
  it with real measurements over time, no curl required.
- The demo bypass for the watcher proved a real Windows issue we now
  track as a known limitation (see "Follow-ups").
- The same `create_app()` factory is used for production, tests, and
  demo — no divergent wiring to keep in sync.

### Negative / trade-offs

- `/v1/demo/*` is in the API surface of the production image. It is
  harmless (no state leakage across calls; can't start a session on a
  non-existent folder) but it could in principle be called against a
  prod deployment. Mitigation: wrap the `include_router(demo_router)`
  in a `settings.demo_enabled` flag in Phase 7 hardening.
- The demo's algo_params overlay is in Python, not YAML. Anyone
  wanting to tweak it for their demo edits `scripts/run_demo.py`
  rather than a committed config version. Acceptable for a demo
  driver, not production.
- In-memory storage means the demo loses everything on Ctrl-C. This
  is intentional and documented — but tripping on it ("where did my
  chassis go?") is now the #1 support question.

### Neutral / follow-ups

- **Fix the Windows watcher buffer** — either switch to
  `PollingObserver` when on `sys.platform == "win32"`, or bump the
  `ReadDirectoryChangesW` buffer explicitly. Needs a follow-up ADR
  once a production-like cadence is chosen.
- **Gate `/v1/demo/*` in production builds** — trivial (`if
  settings.demo_enabled: app.include_router(demo_router)`) but not
  yet wired.
- **Move the replay's band overlay into a named algo_params variant**
  (e.g. `algo-1.3.0-demo.yaml`) rather than a Python `model_copy`, so
  it shows up in version traces.
